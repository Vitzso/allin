In loopback mode the browser reaches the server over loopback only. In network mode it reaches one private address (your WireGuard address) over HTTPS, and nothing else changes about what it may contact. The browser never contacts a provider: the page's CSP, its code paths, and the browser-request tests keep it on the local origin. With a feed on, the **worker** is the only thing that goes online, and the sandbox limits it to port 443, at any address including your local network, and lets it look up any name over DNS, while its own list of two hosts limits where it goes. That second limit is the worker's code, not the OS. On Linux the worker's sandbox limits its file system only: it shares the host's network and can reach any address and port, including `127.0.0.1`, the box's WireGuard address and your home network, over plain HTTP as well as HTTPS, and it can start other programs under `/usr`. It can therefore reach AllIn's own address; AllIn still demands a session cookie and its token for every private request, and the worker has neither. It can't see the vault folder, the key folder or (in the packaged install) the home folders, and it can't write outside its private `/tmp`. The Mac sandbox is the stricter of the two, and narrowing the Linux worker's network needs its own design. It is **not** an OS-level egress guarantee for the rest of the service: no packet capture has been done.

## Market replay contract

`ema-20-50/v3` starts both EMAs at the first close. It publishes no evaluable decision until 50 contiguous closed bars exist. Bar 50 is a no-trigger baseline; a crossover can first occur on bar 51. Upward crossing is a Buy setup, downward crossing a Sell setup, and an evaluable non-crossing bar is No trigger. Gap, changed instrument/provider/venue/currency/calendar/interval, invalid value, out-of-session or off-grid bar, late event, or changed value resets warm-up and yields Signal unavailable, with a reason naming the cause. A bar that has not closed yet yields Signal unavailable but changes nothing, and its final delivery is evaluated normally.

Each bar names its calendar. `continuous` expects a bar every 15 minutes. `us-equity-regular` follows the NYSE regular session, including holidays and 1 p.m. early closes, and the EMAs and warm-up carry from one session's last bar to the next session's first. A whole missing trading day is still a gap. The calendar comes from [NYSE's published dates](https://www.nyse.com/trade/hours-calendars) and covers 2026–2028; bars outside that range are Signal unavailable until the table is extended. Carrying warm-up across sessions is a reversible rule decision: v1 reset at every gap, which meant 26-bar regular sessions could never reach the 50 bars the rule needs.

Only market values identify a change, so a bar redelivered with a new receipt time or revision number is ignored, as is an older revision arriving after a newer one, or an earlier value redelivered at the same revision. A changed value appends a corrected decision; previous replay decisions are not silently rewritten. Evidence contains strategy version, provider, venue, currency, interval, bar revision and receipt time, previous/current EMAs, bar count, time, integer-cent close, and a chained SHA-256 that depends on every bar in the current run. The same inputs produce identical outputs.

Fixture bars represent a deliberately continuous synthetic 20-hour session, including the equity examples. Corporate actions, durable revision journals, backfill reconciliation, and real feed freshness are not simulated. The watchlist is fixed, price views are closing-price lines plus volume, and the journal is regenerated rather than persisted. No AI interprets or generates signals, and no orders, paper fills, wallets, account credentials, or notifications exist.

## Why a rule produces signals, not an LLM

Buy and Sell setups come only from the deterministic rule, as the spec requires. A model must not choose or rank what to buy or sell. It can't be replayed, it has no market data of its own, and text in its inputs could steer it. A confident explanation would also make a weak signal look stronger. In M3 a local model may explain an existing decision using the stored evidence, with tools disabled.

The rule itself has no demonstrated edge. Across 200 seeded zero-drift random walks of 2,880 bars, v3 fired about 56 setups per 30 days. The price was higher about 50% of the time after 4, 16, and 96 bars, with mean moves within noise. Random prices have no edge by construction, so this measures how often the rule fires by chance, not how it performs on real markets. The app shows this next to the rule, and each setup shows its later price move, kept apart from the recorded decision. Real performance needs real data, costs, and the holdout testing the spec describes.

## Differences from PROJECT_SPEC.md

- **Order:** M4 came ahead of the rest of M2 and M3.
- **Polling, not streams:** quotes and signals stay separate, and prices can be about a minute old. A stream can be added later for prices without touching the rule or the stored bars.
- **Credentials:** Alpaca paper keys stand in for market-data-only credentials. No market-data-only key type was found.
- **While locked:** the threat model left this open. A feed you turned on keeps running with the vault locked, so the watched symbols and the Alpaca key stay in memory and requests continue, so that alerts work when you step away. New bars and alerts stay in memory and are saved at the next unlock; if AllIn quits while locked they are lost, and the bars come back on the next catch-up with their setups marked historical.
- **Network mode:** the spec and README keep AllIn local to one machine, with no tunnel or proxy. Network mode is a deliberate exception: HTTPS on your own WireGuard address only, with the Host and Origin checked against a configured origin.
- **Paired devices:** PROJECT_SPEC section 3 asks for explicitly paired, revocable devices for a phone. Network mode doesn't pair devices. It relies on WireGuard peers to decide who can reach the box and on the passphrase to sign in, with a per-device **Sign out** under **Connections & privacy → Signed-in devices**. Pairing isn't built.
- **Linux sandbox:** bubblewrap contains the worker's file system only, where the Mac profile also limits the network and child processes. It is the looser of the two.
- **`sandbox-exec`:** Apple has deprecated it. It's the OS-enforced restriction available without an app bundle. The `pkg` project can revisit it.

## Known limits

The app cannot protect plaintext from an unlocked compromised host, a privileged browser extension, malicious native dependency, or injected code with the app's authority. Browser/OS memory and OS backups are outside the vault's erasure guarantees. Local network membership is not authorization. Network mode (HTTPS on one private WireGuard address, up to three signed-in devices) is a deliberate exception to the loopback-only design, and WireGuard membership alone grants nothing. Anyone on that network can reach the sign-in page, and the sign-in lockout covers the whole server, so a wrong guess from any device delays you too. A browser sends the session cookie to any server on `127.0.0.1`, so the session also requires a token that only this origin can read. A compromised browser profile or extension can still read both.

Both development and production use the same profile unless `ALLIN_DATA_DIR` is set. Development has a broader file-serving and script surface; use disposable synthetic profiles during development. Keep the source and `dist` trusted; lexical static path checks are not a defense against a local attacker who can change deployment symlinks.

There is no signed installer or automatic updater. The Linux install is a script (`scripts/install-linux.sh`, from `npm run package:linux`) that downloads dependencies from the npm registry and has only been checked with `bash -n`; it has never run on a Linux machine. The unit applies four systemd protections and no more, because further ones haven't been tried with bubblewrap. A Mac `.pkg` doesn't exist. There is also no in-app full-vault purge, no passphrase-change dialog, and no feed that runs while AllIn is not running (a feed you turned on keeps running with the vault locked, until you quit). Clean-profile restore rekeys recovered records but does not revoke copies of older backups. An interrupted initial setup may leave unusable encrypted files or an orphaned Keychain entry. Setup then refuses to run until those files are moved, because it cannot tell them from a real vault whose `vault.json` was lost. Never delete existing state before preserving an encrypted copy and confirming recovery.

The independent architecture review identified default-bearing partial-update schemas, UTC/local-day grouping, and mismatched backup size limits. These were corrected and given regression checks. The review was a scoped architecture pass, not a claim of exhaustive vulnerability discovery.
